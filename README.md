# topo

> **一个命令组织多 agent 协作。**
>
> `/topo` 读你的项目、结合当前对话，给出该用哪些 agent、怎么组织、怎么调用，写进 `topo.md`。

## 安装

从 GitHub 安装：

```bash
pi install git:github.com/WanKun824/pi-topo@v0.2.0
```

如果已经发布到 npm，也可以：

```bash
pi install npm:pi-topo
```

就这一步。subagent runner 已经内嵌在包里，不需要另外安装任何东西。

## 用法

```
/topo
```

没有第二个命令。装完直接敲 `/topo`，它会：

1. 读项目实际结构 —— 入口、测试、构建命令、模块边界、近期改动集中在哪
2. 判断这项工作要不要多个 agent，不需要就直接说不需要
3. 需要的话，选角色、定组织形式、给出可以直接用的调用方式
4. 把结论和判断依据写进项目根目录的 `topo.md`

想指定做什么，跟在后面：

```
/topo 把认证模块换成新的 session 存储
```

留空就按当前对话里正在做的事判断。

## `topo.md` 里有什么

产物不是一句「建议用 X」，而是一份可复查的记录：

| 小节 | 作用 |
|---|---|
| **当前方案** | 结论、适用什么工作、判断日期 |
| **怎么调用** | 可以直接粘的调用代码 |
| **项目情况** | 这次判断依据的事实 —— 以后复查就对照这张表 |
| **为什么是这个结论** | 逐条给出判断，没中的也写 |
| **为什么不是别的形式** | 复查时这段往往比「为什么选它」更有用 |
| **角色分工** | 谁负责什么、是否只读、怎么验收 |
| **什么时候该重新判断** | 复查触发条件 |
| **变更记录** | 换过方案就另起一节，不覆盖历史 |

**「项目情况」那张表是以后能不能改方案的全部基础。** 没有它，复查时只能重新凭感觉估一遍。

再跑一次 `/topo` 就是复查：和那张表逐行比，**没变就不要改方案** —— 换方案本身有成本，也会让记录失去可比性。

## 它会说「不用多 agent」

而且经常就是。这是有效结论，不是失败 —— 一个只会推荐协作方案的工具没有用。

工作量大、步骤多、看起来复杂，**都不构成用多 agent 的理由**。值得用的只有这几种情形：上下文独立、能真正并行、能力边界不同、需要隔离、后台长跑。一条都不中，就该单会话做完。

最容易被忽略的反向信号，它会主动点出来：

> **你自己后续需要理解这部分代码时，不要交出去。**
> 交出去的部分你就不熟了，之后每次改动都得重读。

## 可用的角色

沿用内嵌 runner 自带的那一套，装完即可用：

| 角色 | 适合 |
|---|---|
| `reviewer` | 复审代码改动、方案、PR；只读 |
| `oracle` | 对计划/思路要第二意见，挑战假设 |
| `scout` | 摸清一块不熟的代码，可以反问澄清；只读 |
| `researcher` | 查资料、调研外部信息 |
| `worker` | 实际写代码改动 |
| `delegate` | 轻量通用执行，继承父会话模型 |
| `evidence-auditor` | 核查结论有没有证据支撑 |
| `claude-code` / `codex-exec` / `cursor-agent` | 转交给外部 CLI（各有 `-writer` 可写变体） |

`subagent({ action: "list" })` 可查实际清单。只读角色可以放心并行；会写文件的角色同时跑多个，必须确认改的是不同区域，或各自在独立工作区里。

## 能组织成什么样

| 形式 | 用在 |
|---|---|
| **单会话** | 单点改动、需求待定 |
| **一主多从** | 并行复审、并行调研（最划算） |
| **顺序流水** | 有明确先后的交付 |
| **分区并行** | 确认互不干扰的多模块改动 |
| **多方会审** | 重大决策 |
| **按结果扇出** | 目标数量要跑起来才知道 |

通信是**以父会话为中心**的：父会话分发任务、收结果。

**做不到的，本包不假装支持：**

| | 为什么 |
|---|---|
| 子 agent 之间直接对话 | 没有子-子通道，通信严格垂直 |
| 共享黑板 | 子 agent 不能写共享状态；经文件系统共享会有竞态 |
| 竞标 / 拍卖 | 没有这类原语 |

## 什么时候不用它

**你已经知道答案的时候。**

明确是单会话能做完的小改动，或者明确就是要三个 reviewer 并行看一下，都不需要先问。它的价值在**你不确定该怎么组织**的时候。

## 验证

```bash
npm install
npm run check      # typecheck + 测试
```

测试守着几条契约：内嵌 runner 的版本自检不会抛错、vendor 内部无断链 import、vendor 的运行依赖都被本包声明、只提供 `/topo` 一个命令。

### 还没验证的

`/topo` **没在真实 Pi 会话里跑过**。内嵌加载已经逐项验证（版本自检一致、1273 条内部 import 零断链、运行依赖可解析），但 `@earendil-works/*` 这几个宿主 peer 依赖只有在真实 Pi 进程里才存在 —— 实际加载仍需 Pi 环境确认。
